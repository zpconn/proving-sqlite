Appendix A: the loop tests `idx<szHdr` and `d<=nKey` before each field, but nothing bounds how far the varint at aKey[idx] or the value at aKey[d] extends, so a corrupt record makes the decoders read past pKey+nKey (the native probe confirms it: evidence/bringup/08-probes.md), and the comment at 92150-92153 notes the last Mem may then hold uninitialized memory. The proof needs a slack requires, LEDGER.md A-001, whose clause is `__CPROVER_requires(nKey >= 0 && __CPROVER_r_ok(pKey, (size_t)(nKey > 0 ? nKey : 1) + 8))`: the function reads at most max(nKey, 1) + 8 bytes from pKey, whatever p->nField is. Derivation (A-001): the header varint at 92131 reads at most 9 bytes; the loop body (92134) runs only while szHdr <= d <= nKey, since d starts at szHdr and only grows (d += len cannot wrap: d <= 2^31-1 and len <= 2^31-7), so idx < szHdr <= nKey there; the varint at aKey[idx] (92137) and sqlite3VdbeSerialGet at aKey[d] (92143, at most 8 bytes) both end at or before aKey[nKey+7]. nKey >= 0 is needed: a negative nKey wraps (u32)nKey. Prove that bound, and show one byte less fails (builder §2.4): with `max(nKey, 1) + 7` a proof must fail, e.g. at nKey >= 2 on the header {nKey, 6}, whose 8-byte integer at aKey[nKey] ends at aKey[nKey+7], and at nKey = 0 on a 9-byte header varint. If the bound is wrong, report it with the failing trace rather than pick another constant. The loop runs up to nField times (a u16), so it needs a loop contract (PROOF span). The EIGHT_BYTE_ALIGNMENT assert (92130) is compiled out, so p->aMem's alignment is a requires, justified by C-14's ensures (UB-CLASSES.md). sqlite3VdbeMemSetNull's contract requires !VdbeMemDynamic(pMem): show the call at 92153 meets it.
