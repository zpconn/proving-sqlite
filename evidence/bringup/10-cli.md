**Background jobs under Codex.** A separate test (2026-11-08 13:12) started `setsid nohup sh -c "sleep 45; echo … > file" &` and `nohup … &` in one command, then waited 70 s in a second: neither file appeared. Builder §2.9's first option ("start each run in the background with its output in a file") therefore does not work for Codex builders. The builder prompt in campaign.py and proofs/HOWTO.md tell them to run long commands in the foreground with output in a file.

**Usage counting** (GOAL.md §0.8). Both CLIs give a running count, so caps are enforced in tokens and the time-limit fallback is not needed. codex: input_tokens (which already includes cached_input_tokens, the cache reads) + cache_write_input_tokens + output_tokens (reasoning included), from the rollout log, minus the thread's total when the job began, since a resume appends to the same rollout file. claude: input + cache_read + cache_creation + output, summed over messages.

**Usage limits.** Neither limit was hit during bring-up, so the patterns in sessions.toml come from the strings the CLIs ship, read from the binaries. codex: "You've hit your usage limit…" (U+2019 apostrophe), "Usage limit reached", `usage_limit_reached`, and "Try again at <Mon d, yyyy h:mm AM>". claude: "You've hit your limit", "usage limit reached", "Claude AI usage limit reached|<epoch>", "5-hour limit", "weekly limit", and the stream-json `rate_limit_event` with `status` "rejected" and `resetsAt`. Each CLI's exit status at a limit was not observed; campaign.py decides by pattern, not by exit status, and matches only stderr, non-JSON lines and the CLI's own error, failure and rate-limit events, never agent messages. The selftest exercises a limit with a parsed reset time. Claude Code also has an `autoContinueAtUsageLimit` setting, so a Claude session may instead wait out a limit in-process; campaign.py then just sees a long session. Both CLIs report their windows while running (codex `rate_limits.primary.resets_at` in the rollout, claude `rate_limit_event`), which campaign.py can use for reset times.

**Choices.** Claude sessions run in `--permission-mode auto` rather than bypassPermissions: no prompts, and the auto-mode classifier refuses unsafe actions. This orchestrator session's own classifier refused a test launch of `claude -p --permission-mode bypassPermissions`. They also run inside bubblewrap, so a reviewer or ledger session can write only its worktree, /tmp and Claude Code's own state. Codex sessions use `--ignore-user-config`, so Zach's plugins (gmail, github) and default efforts don't leak into builders. campaign.py strips `*_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDECODE` and `CLAUDE_CODE_*` (the orchestrator session's own linkage) from every session's environment.
