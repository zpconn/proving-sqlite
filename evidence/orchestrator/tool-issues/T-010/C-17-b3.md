# C-17 round 3: sqlite3VdbeRecordCompareWithSkip (builder on Claude, Opus 5.5)

Summary:
- **Finding (tested natively):** signed overflow at upstream/sqlite3.c:92793 (`rc = -rc;`). It happens when a collation returns INT_MIN for a DESC key. It is reachable from SQL through the public API, and the repro is tests/repro/F-draft-C-17-1.c. This settles Zach's finding candidate the first of his two ways: a native repro on unmodified upstream.
- **No proof (nothing is proved this round).** Three blockers stop P1 for this function under the frozen pipeline. Each needs a decision only Zach or the orchestrator can make. B1 is the one no harness or contract can get around. The decisions needed are at the end.
  - **B1 (new tool limit):** CBMC 6.11 can't state, and the harness can't build, the per-field pointer obligations (each string/blob Mem's `z` and each non-NULL `aColl[j]`) when the number of fields is unbounded.
  - **B2:** CBMC's memcmp model loops once per byte, so it can't be unwound for unbounded string lengths under `--unwinding-assertions`.
  - **B3:** T-006. The loop carries `pRhs`, and a probe of the real loop hits the encoding blow-up.

So I wrote no files under proofs/C-17/, no contract header, no PROOF span in overlay/sqlite3.c, and nothing in preds.h. The only files this round changes are this report and the repro. Scratch evidence is in tmp/, which git ignores, and everything needed to judge it is quoted below.

Related, for TRUSTED.md (not a finding): memcmp's result reaches the same negation through 92739-92740 and 92767-92768. C11 7.24.4.1 fixes only its sign. ## B1: the per-field pointer obligations can't be stated (new tool limit; proposed tool-issues entry)

What the function needs from pPKey2 is per field, for every field i the loop reaches (i < nField ≤ 65535):
- a MEM_Str Mem (not Int/IntReal/Real) needs `n >= 0` and `r_ok(z, n)`, for memcmp at 92739 and for A-003's requires `r_ok(pMem2->z, pMem2->n)`;
- a MEM_Blob Mem (not Str or numeric) needs the same, or `u.nZero >= 0` with MEM_Zero (92763);
- a non-NULL `aColl[i]` with i < nAllField needs `r_ok(aColl[i], sizeof(CollSeq))`, for A-003's requires.

Real callers do provide these. The Mems come from sqlite3VdbeRecordUnpack or from VDBE registers, and the collations from sqlite3KeyInfoAlloc's users (150533). All of that is outside milestone 1, so it would be a ledger draft. Stating it, though, needs a quantifier over a pointer predicate, and CBMC 6.11 can't do that. Tested on toys in tmp/toy/ (a 20-line contract; `goto-cc --function h`, `goto-instrument --dfcc h --enforce-contract f/contract_f`, then `cbmc --pointer-check --bounds-check --unwinding-assertions`):
- **`forall q in [0,k): a[q].n >= 0 && r_ok(a[q].z, a[q].n)` (np.c):**
  - with MiniSat, every pointer primitive in the requires fails (`pointer invalid in R_OK((u->a + q)->z, ...)`, and 3 more), and so does the dereference `m->z[m->n-1]` it should protect (6 dereference failures);
  - with `--z3`: "SMT2 solver returned error message: unknown constant contract_f::requires::1::q!0@34#0", VERIFICATION ERROR.
- **The same requires for one index j, no quantifier (np2.c):** still `pointer invalid in R_OK` and `pointer outside object bounds` on the dereference (4 of 137 failed). Assuming r_ok doesn't make a pointer valid when it was read from nondet heap memory: CBMC's dereference follows value sets, and the assumption doesn't feed them. So the pointers have to be constructed, by the harness or by DFCC's `__CPROVER_is_fresh`.
- **`is_fresh` inside the forall (np3.c):** goto-cc rejects it: "error: quantifier must not contain function calls", CONVERSION ERROR.
- **The harness can't construct them either:** SETUP may not store through a subscript (scan.py rule 11: "a SETUP assignment may not store through a subscript or a pointer"). It can't write `aColl[k]` at all, and it can set a Mem's `z` only through a fixed set of `m = mem + k; m->z = s;` statements, one per field. A fixed set of statements means a bounded nField.

So for nondet nField, no contract this pipeline accepts makes these paths sound: the string paths at 92716-92744, the blob paths at 92749-92771, and the call at 92734. Leaving the obligations out gives false failures. The probe below leaves them out for that reason.

## B2: memcmp's model has an unbounded loop

`goto-instrument --show-loops` on a toy shows the library's `memcmp.0` (`for(; n!=0; n--)`, <builtin-library-memcmp> line 25). The model first asserts `r_ok(s1, n)` and `r_ok(s2, n)` (its lines 19 and 21), and the loop then only computes the result. Here n is `MIN(mem1.n, pRhs->n)` (92738) or `MIN(nStr, pRhs->n)` (92766), up to (2^32−13)/2 and up to INT_MAX. With `--unwinding-assertions`, which is frozen in CHECKS, the loop needs a bound at least as large as n, so strings and blobs would need a length bound in the requires. vdbeRecordCompareString (C-19, 92975) has the same call.

## B3: T-006 on the real loop (scratch probe)

To check T-006 I ran one scratch probe of the real function with the pipeline's own commands. It is not a proof attempt. Its parts are all under tmp/: the overlay copy tmp/ov/sqlite3.c, and the card directory tmp/probe/C-17 (harness.c and Makefile).
- The PROOF span on the `while(1)` at 92660, which is what I would use:
  ~~~
  __CPROVER_assigns(i, pRhs, d1, idx1, rc, mem1, pKeyInfo, pPKey2->errCode)
  __CPROVER_loop_invariant((bSkip ? 1 : 0) <= i && i < pPKey2->nField
    && pRhs == pPKey2->aMem + i && rc == 0
    && szHdr1 <= d1 && d1 <= (u32)nKey1
    && (i == (bSkip ? 1 : 0) ? idx1 <= (bSkip ? 10u : 9u) : idx1 < szHdr1))
  __CPROVER_decreases(pPKey2->nField - i)
  ~~~
- The probe's contract has every requires except B1's per-field ones:
  - nKey1 >= 0;
  - the record readable for `max(nKey1, 10 + (bSkip != 0)) + 8` bytes (derivation below);
  - `rw_ok(pPKey2, sizeof(UnpackedRecord))`;
  - `nField >= 1 + (bSkip != 0)`;
  - aMem readable for nField Mems;
  - KeyInfo readable for `SZ_KEYINFO(min(nField, nAllField))`;
  - aSortFlags readable for nField bytes.

  Its assigns is `pPKey2->errCode, pPKey2->eqSeen`.
- Every in-scope callee and both boundary callees are replaced by their contracts. The probe also sets `memcmp.0:2`, so that B2 can't keep symex from ending.
- The result, in two runs on lp64-le:
  - **Run 1, default object bits:** "too many addressed objects: maximum number of objects is set to 2^n=256 (with n=8)". No verdict.
  - **Run 2, `OBJECT_BITS := 16`, the largest prove.py allows:** "Solver ran out of memory during propositional reduction. ... Out of memory" after 102 s in all (prove.py: `cbmc gave no verdict (rc 6)`; RSS was 8.9 GB at 74 s, and the machine has 47 GB). This is T-006's failure mode with SAT. I stopped there, as the card asks, and didn't try other solvers or a smaller harness: the B1 obligations would still be missing from any verdict.

## What I would prove, once B1-B3 are decided

Record footprint, derived from the source:
- **First iteration, bSkip 0:** the header varint gives idx1 ≤ 9 (92640-92642), and nothing checks idx1 against szHdr1 before the first type read (92652's assert is compiled out). So the varint at aKey1[idx1] can end at index 17. That is 18 bytes, with nKey1 = 0, a 9-byte header encoding 0, and a string-typed pRhs (getVarint32NR, 92709).
- **First iteration, bSkip 1:** idx1 ≤ 10 (92626-92630), so 19 bytes.
- **Later iterations:** idx1 < szHdr1 ≤ d1 ≤ nKey1 (92805, 92807), so the varint ends by index nKey1+7.
- **Values:** the values at aKey1[d1] are 8 bytes at most (serialGet7, vdbeRecordDecodeInt and sqlite3VdbeSerialGet's contracts), with d1 ≤ nKey1.

So the requires would be `r_ok(pKey1, max(nKey1, 10 + (bSkip != 0)) + 8)`, the A-001 slack for this card. This is a derivation; no run has shown it to pass or fail. The other requires are listed under B3 and B1, and every one of them has to hold at the in-scope call sites:
- sqlite3VdbeRecordCompare (92832) passes bSkip 0;
- vdbeRecordCompareInt (92922) and vdbeRecordCompareString (92985) pass bSkip 1, and only when `nField>1`, which satisfies `nField >= 2`.

The cards that inherit C-17's contract inherit B1 too: C-18, C-19 and C-20 (C-19 also has B2 through its own memcmp).

2. **Record B1 as a tool issue.** The toys are quoted above and can be rerun from their descriptions. It is separate from T-006: CBMC's legacy contracts (T-006 option 1) have the same rule against memory predicates under quantifiers, as far as I know, but I haven't tested that.
3. **What C-17 should claim.** Options as I see them:
   - (a) **A bounded P1.** nField ≤ K with the loop unwound, string and blob lengths ≤ L for memcmp, and the harness building each field's pointers. This needs a PROPERTIES.md change, because the loop is not bounded by construction at 16 or fewer, and a scan.py rule for writing `aColl[k]` in SETUP. Both are frozen-file changes.
   - (b) **A memcmp contract** in place of the model: its own two r_ok preconditions, assigns nothing, any int result. That solves B2 alone, with a TRUSTED.md and LEDGER.md entry, and with an "any int" result the memcmp paths would reach the 92793 negation as well (see the TRUSTED.md note above).
   - (c) **Park C-17 (and C-18, C-19, C-20) as tested only,** through the ledger agent or native runs.

   I recommend (c) for now, with (a) as a later, clearly labelled bounded result if Zach wants a CBMC claim. Every unbounded route needs a tool CBMC 6.11 isn't.
