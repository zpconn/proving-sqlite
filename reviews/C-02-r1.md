## Checklist
1. **SQLite's code.** The diff touches only proofs/C-02/{harness.c,Makefile,NOTES.md} and reports/C-02-b1.md. overlay/ and upstream/ are unchanged. The harness `#include`s sqlite3.c and calls all five functions plus the real `getVarint32` macro.
2. **Bytes unconstrained.** `value` (u64), the 9-byte `buffer` and `extent` are uninitialized nondet locals. The only assume is in SETUP: `extent` in [1,9] and `encoded != 0`. Both are sizes and allocation, not data bytes. The decoder input is copied from the encoder's output, not assumed.
3. **Requires.** The card has no in-scope callers and no requires. I deleted or changed each setup condition in scratch copies (lp64-le):
   - `buffer[8]`: FAIL (364/450 non-success properties, `sqlite3GetVarint.pointer_arithmetic.4` and `.5` at line 38024).
   - `malloc(extent-1)`: FAIL (349 failed, `sqlite3GetVarint.pointer_dereference.13` and `.14` at line 38025). It is the same failure as the report's n-1 case.
   - Removing `assume(encoded != 0)`: FAIL (349 failed, `sqlite3GetVarint.pointer_dereference.13` and `.14`, pointer NULL in `*p`). This is a malloc-may-fail artifact of the harness, not SQLite.
   - The footprints are therefore tight. Exact n decoder bytes pass and n-1 fails. The nine-byte encoder buffer passes and eight fails.
4. **Not vacuous.**
   - I put `__CPROVER_assert(0)` inside the `extent == n` decoder branch. It FAILS (`assertion.4`, "reach"), so the branch is reachable. Because `extent` is independent of `value`, every n in [1,9] has a matching allocation. The branch excludes no value.

   - All 11 mutants are killed.
5. **Ensures and assigns.** There are no function contracts.
