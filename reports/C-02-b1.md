Contract: this is a relational harness, not a separately enforceable function
contract. It gives sqlite3PutVarint a local nine-byte buffer whose initial bytes
are arbitrary. It checks n in [1,9] and equality to the saved initial byte at
every index >= n; bounds checks exclude writes outside the nine-byte object.
Each decoder receives a fresh allocation of exactly n bytes copied from that
encoding, with distinct typed local output objects. The returned lengths equal
n; decoded64 equals the original value; decoded32 equals that value up to
0xffffffff and 0xffffffff above it. VarintLen equals n below 2^63 and 10 above
or at 2^63. The encoder's external writes are its output prefix; each decoder
stores its result through its output pointer. There is no DFCC assigns clause
on this card; its requested buffer frame condition is checked by assertions.

Requires and justification: there are no in-scope callers on C-02. Nine writable
encoder bytes and valid output objects are supplied by local declarations.
SETUP selects an independent extent in [1,9], allocates that many bytes, and
requires successful allocation. The decoder branch runs when extent==n.
Because the proof establishes n in [1,9] for every value, each value has a
matching allocation; the branch excludes no input value from the round trip.
The exact n encoded bytes are produced by execution, never assumed. The
requires/counterexample table is in proofs/C-02/NOTES.md.

Footprint and setup negative checks (lp64-le, all checks, complete RESULT lines):

- Eight encoder bytes fail `putVarint64.pointer_dereference.5`, an out-of-bounds
  `p[8]` write at upstream/sqlite3.c:37971, for v=0x40000000fffffffe.
- Allocating and copying n-1 decoder bytes fails bounds. One counterexample is
  v=0, n=1, with a zero-byte allocation and the first read at
  upstream/sqlite3.c:38024 (`sqlite3GetVarint.pointer_dereference.5`).
- Removing the successful-allocation assumption allows malloc to return NULL;
  the prefix-copy destination and decoder input then fail pointer checks.

These are deliberately invalid harness allocations, not SQLite findings.
The first two runs report 364/450 and 330/451 non-success properties, respectively;
the NULL run reports 349/450. The runner includes UNKNOWN in those counts after
an invalid access. The concrete FAILURE properties above, rather than those
aggregate counts, establish the negative checks.
