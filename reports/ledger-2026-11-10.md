# Ledger validation — 2026-11-10

Ledger agent (Claude Code, Opus). I tested LEDGER.md's five assumptions (A-001 to
A-005) against SQLite 3.53.4 itself, built from the pinned source release, by
instrumenting each assumption's site with a check that **logs without aborting**
when the assumption fails, counts every time the site is reached, and records a
backtrace. I then ran SQLite's own test and fuzz targets. This is *tested*
evidence: how often each assumption held or failed in these runs, and nothing
more. I did not touch proofs, contracts, the overlay, LEDGER.md or FINDINGS.md,
and nothing left the machine.

**Headline:** A-002, A-003 and A-004 are **tested** with zero violations. A-005 is
**tested** memory-safe (no write ever left its buffer) but its clause overstates
what callers do. **A-001 is violated**: several real caller paths hand
`sqlite3VdbeRecordUnpack` a record with no readable slack, and on a crafted corrupt
record one of them (`sqlite3_preupdate_old`) overreads the heap. Repro against
unmodified upstream below. This is a **finding draft (F-002)** for the
orchestrator, not a defect in any proof — the proof's `requires` is the correct
worst case; what fails is the *caller obligation* the ledger attributes to
milestone 2.

## 1. Build (GOAL.md §1)

- `upstream/sqlite-src-3530400.zip` matches its pin.txt sha256; `manifest.uuid`
  inside is the pinned check-in `bf7c7f30…9bcc`. Unpacked to `validation/src/`.
- Rebuilt the amalgamation from that tree (`validation/build/amal`): it equals
  `upstream/sqlite3.c` **byte for byte**.

  (`diff -ruN` removed-lines = 0, 635 added). Re-applying it with `patch -p1` to a
  fresh unpack reproduces the tree. The patched amalgamation
  (`validation/build/lamal/sqlite3.c`) equals `upstream/sqlite3.c` plus the
  inserted lines; the single non-insertion diff is `SQLITE_SOURCE_ID`, whose last
  7 hex chars the amalgamator rewrites to `alt1` because the tree is modified
  (`evidence/ledger/2026-11-10/patched-amalgamation.diff.txt`).
- The checks: for the memory-extent assumptions (A-001, A-002, A-003 strings,
  A-005) `__asan_region_is_poisoned` from `<sanitizer/asan_interface.h>` measures
  the addressable bytes; for struct-field / return-value / assigns assumptions
  (A-002 alignment and size, A-003 and A-004 "assigns nothing visible", A-004
  return value) the fields and results are checked directly. Every check has a
  counter, and memory-extent sites also keep a histogram of the addressable bytes
  seen. Counters live in an `mmap(MAP_SHARED)` file per process so a crash can't
  lose them; violations append an entry-ID + arguments + backtrace to a log.
- **Each check is shown to work** (`validation/demo/`, 34 cases, ASan and non-ASan):
  every deliberate violation is logged with its entry and kind, each control logs

## 3. Results per entry

Counts below are summed over the ASan runs unless noted (the non-ASan builds in
`test` reach the sites but skip the ASan-based checks). Full tables:
`evidence/ledger/2026-11-10/summary.md` and `summary.json`; per-site reach lists
`reach-*.tsv`; raw violation records `violations-*.txt(.gz)`.

### A-001 — Readable slack after a record — **VIOLATED**

- Site `sqlite3VdbeRecordUnpack` entry reached **~14.4M** times (sdevtest), ASan-checked
  **6.85M** times there; also exercised under every other ASan target.
- Slack after the record (addressable bytes past `pKey+nKey`): **minimum 0**, seen
  with 0 slack in 4,136 measurements and <8 ("short", below the required 8) in
  ~153k. Violations logged where slack < required: **151,429** (sdevtest), 665
  (test's asan build), 124 (fuzztest-asan), 665 (fuzzcheck-native).
- The caller paths that reach the site with insufficient slack (by backtrace):
  1. `sqlite3_preupdate_old` → `vdbeUnpackRecord`: `aRec = sqlite3DbMallocRaw(db, nRec)`
     where `nRec = sqlite3BtreePayloadSize(on-disk cursor)` — **exact size, no padding**,
     and the bytes come from the file, so they can be corrupt (upstream 95940/95888).
  2. `sqlite3_preupdate_new` (UPDATE path) → `vdbeUnpackRecord`, same shape.
  3. `sqlite3BtreeInsert` BTREE_SAVEPOSITION path: `pCur->pKey = sqlite3Malloc(pX->nKey)`
     — exact size, no padding (upstream 82920).
  4. `vdbeSorterCompare` (the sorter) → `sqlite3VdbeRecordUnpack`.
  5. `btreeMoveto` ← `btreeRestoreCursorPosition` ← `btreeNext`, restoring a cursor
     whose `pCur->pKey` came from path 3 (no padding).
- **Contrast:** `saveCursorKey` (the other restore source, upstream 73957) allocates
  `nKey + 9 + 8` and `memset`s the 17 padding bytes, with a comment that
  `sqlite3VdbeRecordUnpack` "may overread the buffer by up to the size of 1 varint
  plus 1 8-byte value." SQLite's developers know about this overread and pad **that**
  buffer — but not the preupdate or insert-saveposition buffers.

**Reading.** SQLite really calls `sqlite3VdbeRecordUnpack` on exact-size, corrupt-able
records with no slack. The assumption as a clause CBMC takes is correct and tight
(the proof needs `max(nKey,1)+8`), but the **caller obligation** A-001 assigns to
milestone 2 ("whoever passes an nKey-byte record also makes 8 more bytes
readable") is **not met** by paths 1-4. In the suites no actual overread fired,
because the corrupt records present never pushed a read past the (short) live
region; but the worst case the proof requires **is** reachable, which I show with
a repro that forces it. → **finding draft F-002**, §4.

- *Site branch not reached:* the `nKey == 0` sub-case (empty record, needs 9 slack
  bytes) was never exercised — `LH_A001_N0` total 0. The nKey>0 slack is what the
  suites reach. Not evidence either way for the empty-record derivation.

### A-002 — `sqlite3DbMallocRaw` returns NULL or a fresh ≥n, 8-aligned block — **TESTED, 0 violations**

- Checked at the `sqlite3VdbeAllocUnpackedRecord` call site: alignment (`&7==0`),
  size (`sqlite3DbMallocSize ≥ n`), and (ASan) the n bytes addressable.
- Reached **~1.03M** times, ASan+field-checked **514,651** times (sdevtest).
  **0 violations.** Every returned block was 8-aligned, at least `n` bytes, and
  addressable; NULL returns counted separately and are allowed.

### A-003 — `vdbeCompareMemString` compares two strings, assigns at most `*prcErr` — **TESTED, 0 violations**

- Two checks. (a) At the C-17 call site: the `requires` (both Mems and the CollSeq
  readable, both `z[0..n)` readable, `prcErr` writable), plus an **assigns** check
  that hashes every caller-visible object before and after the call (`*pMem1`,
  `pMem1->z`, `*pMem2`, `pMem2->z`, `*pColl`, the whole `UnpackedRecord` with errCode
  masked, `aMem[]`, the KeyInfo with `aColl[]`+`aSortFlags[]`, and `pKey1[0..nKey1)`)
  and reports any change other than `*prcErr`. (b) At the function entry, the
  `requires` for every caller.
- C-17 call site reached **3.22M** times, assigns-checked 524,192 times; entry
  reached **23.7M** times (sdevtest). **0 violations** of either the requires or
  the assigns. The collation callbacks and the encoding-change path changed nothing
  the caller can see beyond `*prcErr`. (Encoding-change path `LC_A003_ENCCHANGE` and
  `*prcErr` writes were counted; both occurred and neither broke the clause.)

### A-004 — `sqlite3CorruptError` returns SQLITE_CORRUPT, changes nothing visible — **TESTED, 0 violations (low volume)**

- At the comparators' `SQLITE_CORRUPT_BKPT` sites, the return value is checked ==
  SQLITE_CORRUPT and the caller-visible record state is hashed before/after.
- Reached **945** (test) / 231 (fuzzcheck-native) / 172 (fuzztest-asan) times — the
  site only fires on a corrupt record inside the comparators, so volume is low but
  **nonzero**. **0 violations**: every call returned SQLITE_CORRUPT and changed
  nothing visible. The default log callback was not installed in these runs
  (`LC_A004_XLOG_SET` 0); the clause's risk is an *application* log callback, which
  these suites don't register, so this tests the return/assigns half, not a
  scribbling callback. Noted as a coverage gap, not a violation.

### A-005 — Nine writable bytes at a varint's output — **TESTED memory-safe; clause overstated**

- At `sqlite3PutVarint` and `putVarint64` entry, the addressable bytes at the output
  pointer are measured, and `LC_A005_REAL_OVERFLOW` counts any call where the bytes
  actually written would exceed the addressable region.
- Reached ~**100M** (`sqlite3PutVarint`) / ~**25M** (`putVarint64`) times.
  `LC_A005_REAL_OVERFLOW` = **0** across every run. But the output buffer held **9**
  bytes only rarely: the minimum addressable seen was **4** (`sqlite3PutVarint`) /
  **5** (`putVarint64`), and "violations" (addressable < 9) numbered 6,518 + 363
  (sdevtest). Every one had the written length ≤ addressable.
- The dominant short-buffer caller is `OP_MakeRecord` (`sqlite3VdbeExec`), which sizes
  the header buffer to the exact total header length and writes each serial-type
  varint into its slot, so only `VarintLen(serial_type)` bytes remain — never 9, but
  always enough for that `v`.

**Reading.** The assumption is **not wrong for the proof** — CBMC must assume a
worst case, and 9 bytes is the tight worst case (a v ≥ 2⁵⁶ needs all 9). But the
clause's plain English and "who must make it true" ("callers provide nine writable
bytes starting at the output pointer") describe something real callers **do not do**:
they provide at least `sqlite3VarintLen(v)` bytes for the specific `v` they pass.
No memory-safety issue (0 real overflows). Suggest the ledger reword A-005's caller
obligation as a per-call coupling — "a caller passing `v` provides at least
`sqlite3VarintLen(v)` writable bytes, which is 9 when v ≥ 2⁵⁶" — so it matches what
`OP_MakeRecord` and the other writers guarantee. This is a **ledger-wording note for
the orchestrator**, not a finding.

### Comparator slack (measurement for the open S values in A-001)

A-001 leaves the comparators' slack `S` unfixed ("each card determines the
smallest that works"). Measured addressable bytes after the record at each entry:

| Comparator entry | min addressable seen | note |
|---|---|---|
| `sqlite3VdbeRecordCompareWithSkip` | **0** | general path; no padding guaranteed |
| `vdbeRecordCompareInt` | **≥160** (histogram cap) | only chosen when padding is guaranteed |
| `vdbeRecordCompareString` | **≥160** (histogram cap) | same |

This matches `sqlite3VdbeFindCompare`'s comment that the optimized `Int`/`String`
comparators are only selected when callers guarantee ≥74 bytes of padding: in
practice they always saw ≥160. The general `WithSkip` path saw as little as 0. Data
point for whoever fixes `S` on C-17/C-19/C-20.

## 4. Finding draft F-002 (for the orchestrator; I did not write FINDINGS.md)

- **Function, line, check, config:** `sqlite3VdbeRecordUnpack` reads past the record
  buffer; the read is in `serialGet`/`sqlite3VdbeSerialGet` (upstream 91950/92064)
  and `getVarint32` (92137), reached from `sqlite3_preupdate_old` →
  `vdbeUnpackRecord` → `sqlite3VdbeRecordUnpack`. ASan heap-buffer-overflow, native
  x86-64, `-O1 -fsanitize=address`, `-DSQLITE_ENABLE_PREUPDATE_HOOK
  -DSQLITE_ENABLE_DESERIALIZE`.
- **Counterexample:** a one-row table `t(a BLOB, b INTEGER)` with `b` encoded as a
  1-byte integer (serial type 1). Flip that serial type to 6 (8-byte integer) in the
  database image, so the header claims an 8-byte value at offset 1999 of a 2000-byte
  record. A `DELETE` with a pre-update hook that calls `sqlite3_preupdate_old(db, 1, …)`
  makes SQLite copy the on-disk payload into `sqlite3DbMallocRaw(db, 2000)` — no
  padding — and decode it, reading 7 bytes past the allocation.
- **Repro:** `evidence/ledger/2026-11-10/repro/preupdate_old_overread.c`, built
  natively against unmodified `upstream/sqlite3.c`. `… clean` is the control (no flip,
  no report); no argument triggers the overread. ASan output saved as
  `preupdate_old_overread.asan.txt`. (Kept under validation/evidence per my write
  scope; the orchestrator can move it to `tests/repro/F-002.c`.)
- **Reachable from SQL or the public API?** Yes, with `SQLITE_ENABLE_PREUPDATE_HOOK`:
  open/attach a corrupt database file (or `sqlite3_deserialize`) and run a `DELETE`/
  `UPDATE` while a pre-update hook is registered and calls `sqlite3_preupdate_old`/
  `_new`. The sorter and `sqlite3BtreeInsert` BTREE_SAVEPOSITION paths reach the same
  decoder with unpadded buffers (seen in the runs) and may be reachable without the
  pre-update feature; I did not build a standalone repro for those.
- **My reading:** `saveCursorKey` deliberately pads its restore buffer by 17 bytes
  against exactly this overread, so the fix precedent already exists in the tree; the
  preupdate and insert-saveposition buffers lack the same padding. Either those call
  sites should pad (`+9+8`, or round up and zero), or A-001's caller obligation has
  to name these paths as ones that don't yet satisfy it. **Status: reproduced.** I
  did not report it upstream (AGENTS.md §7) — it stays here until Zach decides.
